이는 열 이름이나 실행 방법의 보완과 달리 전송 대상의 제외입니다. `I/intent.md`의 waiver는 게이트 손 수정 한 건뿐이고, `I/spec.md`에도 이 범위 변경의 추가 승인이 없습니다. 설계상 타당성 여부와 별개로, 승인 후 작업 범위 변경 절차를 지키지 않았습니다.

### A-2. 태그 수정 커밋에 별개 기능의 한계 기록을 섞었습니다 — 위반

`a865f1d`는 W-16/S-16의 npm 태그 대상 수정과 함께 `I/spec.md`에 동기화 자연 키 중복의 한계를 추가했습니다. 자연 키 한계는 W-8·W-9의 리뷰 결과이며 npm 태그 수정과 독립적입니다.

이 커밋 전체를 되돌리면 발행 로직뿐 아니라 동기화 한계 기록도 사라집니다. “무관한 작업을 한 커밋에 섞지 않는다”는 의미 단위 규칙의 경미한 위반입니다.

### A-3. package.json과 lockfile 동시 변경 규칙에 예외를 기록하지 않았습니다 — 문언상 위반

`d7604c1`은 desktop의 `test` 스크립트를 추가했고 `416c504`는 루트의 `release` 스크립트를 바꿨지만, 두 커밋 모두 `pnpm-lock.yaml` 변경이 없습니다. 당시 `AGENTS.md`와 `.agents/knowledge/2026-10-25_frozen-lockfile.md`에는 스크립트만 변경하는 경우의 예외가 없습니다.

다만 의존성 변경은 없고 `R/pr-118-quality-job.log`의 frozen install도 성공했습니다. 따라서 lockfile 불일치나 설치 결함을 발견했다는 뜻은 아닙니다. 규칙의 문언과 실제 적용 사이의 경미한 불일치입니다.

### A-4. 일부 검사에서 세부 조건의 증적 없이 전체 PASS로 처리했습니다 — 위반

`R/test/report.md`는 V-11 전체를 PASS로 판정하지만, 인용된 `suite-EFGI.log`의 V-11 출력은 배치 분할·충돌 두 종류·invalid_commit만 다룹니다. spec의 “요청 전송 중 같은 행을 다시 편집하고 ack 뒤 보존 확인”은 나타나지 않습니다. `R/review-response.md`도 관련 타이밍 재현을 하지 않았다고 명시합니다. 응답을 잃은 다음 라운드에 편집하는 E2E는 이 검사와 동일하지 않습니다.

또한 V-10의 로그아웃 초기화는 있지만 서버 변경 시 초기화·큐 보존의 실행 결과는 인용 로그에 없습니다. V-15의 오프라인 복구·디바운스는 있지만 백오프 간격 증가를 확인한 결과는 없습니다. 해당 세부 조건의 충족은 **확인 불가**인데, 보고서는 V 전체를 PASS로 표시했습니다.

V-2에는 여전히 `src/common/*.test.ts` 실행이 명시되어 있지만 실제 러너와 로그는 `test/**/*.test.ts`를 사용합니다. 테스트 실행 자체는 확인되지만 “spec대로 실행했다”는 기록은 정확하지 않습니다.

### C-1. 리뷰 종결에 필요한 기록이 부족합니다 — 확인 불가

`R/review-response.md`는 finding 7을 “받아들이지 않음”, “사용자 판단 요청”으로 남겼습니다. 이후 사용자 결정이나 `pl/discussion` 기록은 제공된 증적에 없습니다. 실제 stage SHA와 버전 변경 커밋의 차이를 감수하기로 승인받았다고 볼 수 없습니다.

### C-2. 외부 작업 허가·브랜치 정리의 증적이 부족합니다 — 확인 불가

PR 병합자가 사용자 `bluenyang`이라는 사실은 확인됩니다. 이를 에이전트의 무단 병합으로 판정하지 않습니다. 다만 그 이전 push·PR 생성에 대한 사용자 허가 원문이나 허용 설정은 읽은 기록에서 확인되지 않습니다.

현재 로컬·원격 추적 브랜치에는 작업 브랜치가 없지만, 네트워크 없이 원격 브랜치 실제 삭제나 삭제 실행 결과를 확인할 수는 없습니다.

### C-3. 최종 상태 기록이 서로 다릅니다 — 기록 보완 필요

`.loctx/ROADMAP.local.md`는 intent 승인 대기, `.loctx/history/1.3.0.md`는 PR 생성 단계와 수동 검사 대기를 남겨 두었습니다. `R/pr-118.json`의 PR 본문도 일부 수동 검사를 미완료로 표시하지만 `R/test/report.md`에는 사용자 확인 완료가 있습니다.

## 해결 방법

1. **A-1은 PM이 범위 변경을 사용자에게 명시적으로 제시해야 합니다.** tombstone 제외의 이유와 영향, 원래 범위를 구현하는 대안을 비교하고 사용자의 수정 또는 수용 결정을 기록해야 합니다. 필요하면 `pl/discussion` 또는 `advisor/committee`의 의견을 받아야 합니다. 사후 수용은 당시 승인이 있었다는 뜻으로 소급 기록하지 않아야 합니다.

2. **A-2 때문에 master 이력을 다시 쓰지 않아야 합니다.** 현재 spec의 자연 키 한계 기록을 유지하고 이번 커밋 경계 위반의 처리 결정을 남기는 것으로 수습할 수 있습니다. 이후 기능별 수정과 별개 한계 문서는 각각의 관련 커밋에 넣어야 합니다.

3. **A-3은 불필요한 lockfile 변경으로 해결하지 않아야 합니다.** PM은 frozen install 성공과 스크립트만 바뀐 diff를 근거로 이번 예외 수용을 요청해야 합니다. 향후에는 사용자가 동의한 경우 “설치 해석에 영향을 주는 manifest 변경은 lockfile과 함께 커밋한다”는 식으로 규칙을 명확히 할 수 있습니다.

4. **A-4는 검사별 하위 조건 표로 보완해야 합니다.** V-11 in-flight 재편집, V-10 서버 변경 초기화, V-15 백오프 증가에 기존 원본이 있으면 연결하고, 없으면 실행 후 원본을 남겨야 합니다. 그전에는 해당 부분을 확인 불가 또는 미완료로 표시해야 합니다. V-2의 실제 테스트 경로도 spec과 맞춰야 합니다. `database is locked` 중단의 원인과 재실행 방법도 보고서에 보완해야 합니다.

5. **C-1은 리뷰를 닫는 기록이 필요합니다.** PM은 finding 7에 대한 해결안 또는 한계 수용을 사용자에게 제시하고, 미해결 의견 차이에 필요한 논의 기록을 확보해야 합니다. 지정 리뷰어에게 최종 TLS·스텁 변경을 검토하게 한 뒤 결과를 첨부해야 합니다. 본 감사는 그 리뷰를 대신하지 않습니다.

6. **C-2는 PM이 기존 허가·정리 기록을 제공해야 합니다.** 실제 있었던 허가 원문과 브랜치 삭제 결과만 추가해야 합니다. 기록이 없으면 확인 불가 상태를 유지하고 사용자 처리에 명시해야 합니다.

7. **C-3은 로컬 로드맵·history·최종 테스트 상태를 정리해야 합니다.** PR head `ca6ff95`와 병합 결과 `35c171d`의 동일 트리, 승인 rev와 병합된 커밋의 대응을 남겨야 합니다. 원본 PR 수집 파일을 고쳐 과거 상태를 지우지 말고 후속 상태 기록을 추가해야 합니다.

8. **V-19·V-20은 사후 검사로 계속 관리해야 합니다.** stable 게시 직후의 업데이트 확인과 첫 Changeset 발행 때의 staging 확인에 각각 담당자·실행 시점·증적 경로를 남겨야 합니다. macOS 검증 한계는 릴리스 노트에 명시해야 합니다.

감사자는 해결안에 대한 PL·Advisor 의견이나 사용자 수용을 새로 받은 것으로 기록하지 않습니다. PM이 위 항목을 처리하고 사용자 결정을 아래에 채운 뒤 감사 기록을 커밋해야 합니다.
