4. **V-15 영·한 내용 대칭:** `R/v15-docs-and-release-note.log`는 키워드 개수·제목·예시 존재를 보여 주지만 여섯 항목의 의미상 대칭 검토 결과는 없습니다. `stale 0.1.0 wording count=1`의 해당 문장과 허용 이유도 없습니다. 실제 문서 오류를 단정하지 않으며 이 세부 조건은 **확인 불가**입니다.

test skill은 적힌 기대 결과로 판정하고 모호하면 실패로 돌리도록 합니다. 확인된 실행은 유지하되 미확인·불일치까지 전체 PASS로 덮어서는 안 됩니다.

### C-1. 최초 push·PR 생성의 사전 허가를 확인할 수 없습니다 — 확인 불가

`R/push.log`와 PR 기록은 외부 실행을 보여 줍니다. H에는 이력 재작성 선택, 사용자 직접 force-push 원문 “force-push 해놨음.”과 이후 병합 지시가 있습니다. 그러나 최초 push·PR 전에 이를 허용한 원문이나 설정은 제공 기록에서 확인되지 않습니다.

이를 에이전트의 무단 force-push나 무단 병합으로 판정하지 않습니다. 사용자 직접 실행과 배포 역할의 금지 행위는 구분합니다. 이후 병합 허가를 최초 외부 작업의 사전 허가로 소급할 수는 없습니다.

### C-2. 원격 브랜치 삭제 실행 원본이 부족합니다 — 확인 불가

H는 원격·로컬 작업 브랜치와 로컬 backup 삭제를 기록합니다. 현재 로컬 `git branch -a`에도 이 브랜치들은 없습니다. 다만 `R/merge.log`는 master fetch·fast-forward 출력으로 `--rebase --delete-branch` 명령이나 원격 삭제 성공 출력을 담지 않습니다. 원격 추적 ref 부재만으로 서버 측 삭제를 확정할 수 없습니다.

rebase 병합은 PR JSON과 선형 커밋·동일 트리로 확인됩니다. 부족한 것은 원격 정리 실행 원본이며 네트워크로 보충하지 않았습니다.

## 해결 방법

1. **A-1:** 병합된 master 이력을 다시 쓰지 않아야 합니다. PM은 이번 커밋 경계 위반의 수용 여부를 제시하고 이후 토큰·OTP·metrics 수정은 기능별로 묶어야 합니다. 같은 결함의 코드·테스트·문서는 함께 둘 수 있습니다. 경미한 절차 위반으로 PL 의견을 받아 재발 방식을 정리하는 것이 적절합니다.
2. **A-2:** 지정 리뷰어에게 최종 head, 기존 리뷰 이후 차이, 재작성 fixture 차이를 전달하여 후속 리뷰를 받아야 합니다. 결과 SHA·경로를 H에 남기고 수정이 필요하면 별도 브랜치에서 리뷰·검사 후 병합해야 합니다. 사후 리뷰를 당시 리뷰로 적어서는 안 됩니다. 승인된 재발 방지 결정의 반복 위반이므로 PM은 `pl/discussion` 또는 `advisor/committee`로 원인·병합 직전 확인 절차에 대한 의견을 받고 사용자에게 수정 또는 수용을 요청해야 합니다.
3. **A-3:** V별 하위 조건을 실행 확인·불일치·미확인으로 분리해야 합니다. runner 역할·skip 및 오류 JSON 문구는 기존 protocol과 대조한 정정안을 검사 설계자나 PL이 검토하고 사용자 승인 후 spec에 반영해야 합니다. V-13의 다섯 테이블·양쪽 outbox·클라이언트 로그·토큰 경로는 기존 원본을 제출하거나 부족한 검사를 실행해야 합니다. V-15는 여섯 항목 대조와 옛 문구의 맥락을 기록해야 합니다. 제외가 필요하면 사용자 결정과 필요한 waiver를 남겨야 하며 감사자가 대신 승인하지 않습니다.
4. **C-1:** PM은 실제 존재했던 최초 push·PR 허가 원문과 시점을 제공해야 합니다. 없으면 확인 불가로 유지하고 사용자 처리에 명시해야 합니다. 이후 허가를 이전 허가로 바꾸어 적지 않아야 합니다.
5. **C-2:** 보유한 삭제 명령·결과 원본을 제공해야 합니다. 없으면 향후 확인을 추가하되 사후 확인이라고 표시해야 합니다. 감사자는 원격 조회나 삭제를 하지 않습니다.
6. **기록 정리:** `test-summary.md`의 HEAD `d405438`, PR 본문의 옛 수정 SHA와 최종 head 관계는 위 대응표로 보존해야 합니다. 로컬 로드맵의 “다음: 0.1.1”도 현재 단계와 맞추어야 합니다. 원본 PR·실패 로그는 덮어쓰지 말고 후속 상태를 별도로 남겨야 합니다. 취약점 패치 지시와 향후 rc는 별도 범위를 확정해 진행하며 이번 감사가 그 작업을 완료한 것은 아닙니다.
